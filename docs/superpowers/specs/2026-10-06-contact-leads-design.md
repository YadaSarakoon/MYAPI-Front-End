# ระบบรับคำขอติดต่อ MyAPI

## เป้าหมาย

ลูกค้าส่งฟอร์มหน้าเว็บเดิมได้จริง ทีมเปิดดูข้อมูลย้อนหลังและติดตามสถานะได้ พร้อมอีเมลแจ้งเตือนเมื่อมีคำขอใหม่ ข้อมูลต้องถูกบันทึกก่อนแสดงผลว่าส่งสำเร็จ และไม่สูญหายเมื่อระบบอีเมลขัดข้อง

## สภาพโปรเจกต์ที่ตรวจพบ

- React + TypeScript + Vite มี Firebase Authentication สำหรับสมาชิก
- `src/features/landing/PastelSections.tsx` ปัจจุบันป้องกันการ submit และแสดงข้อความว่ายังส่งไม่ได้ ไม่มีการบันทึก
- ยังไม่มี Firestore, Cloud Functions หรือบทบาทแอดมินในโค้ดที่ตรวจพบ
- มี API client แยกอยู่แล้ว แต่ยังไม่มีหลักฐานว่า backend เดิมรองรับคำขอติดต่อ

## ขอบเขตรุ่นแรก

1. ใช้ฟอร์มหน้าตาเดิม ตรวจช่องที่จำเป็น แสดงกำลังส่ง/สำเร็จ/ผิดพลาด ป้องกันกดซ้ำ และเก็บค่าที่กรอกไว้เมื่อส่งไม่สำเร็จ
2. เพิ่ม Firebase callable function รับคำขอแบบไม่ต้องล็อกอิน ตรวจข้อมูลฝั่ง server และบันทึกใน Firestore
3. เพิ่มหน้าทีม `/admin/leads` แสดงรายการใหม่ก่อน ค้นหาในหน้าที่โหลด ดูรายละเอียด เปลี่ยนสถานะ และบันทึกโน้ต แบ่งหน้าเพื่อไม่โหลดข้อมูลทั้งหมด
4. สถานะคำขอ: `new`, `contacted`, `closed`
5. ส่งอีเมลแจ้งเตือนไปยังผู้รับที่ตั้งค่าฝั่ง server ไม่มีอีเมลตอบกลับอัตโนมัติถึงลูกค้าในรุ่นแรก
6. การแจ้งเตือน LINE และระบบ CRM ขั้นสูงอยู่นอกขอบเขตรุ่นแรก

## โครงสร้างและข้อมูล

- ใช้ Firebase project เดียวกับ Authentication เดิม โดยต้องตรวจ project ที่จะ deploy ก่อนเปิดใช้งานจริง
- Collection `contactLeads`: company, fullName, phone, email, website, courier, createdAt, updatedAt, status, note
- Server กำหนดเวลาและสถานะเริ่มต้นเอง ตรวจชนิดข้อมูล ความยาว และรูปแบบ email/URL รวมถึงจำกัดช่องที่ยอมรับ
- ใช้ submission ID ที่สร้างฝั่ง client และเก็บไว้สำหรับ retry เดิม เพื่อให้การส่งซ้ำหลังเครือข่ายขาดไม่สร้างรายการซ้ำ Server ใช้ transaction และไม่คืนข้อมูลส่วนตัวจากรายการเดิม
- เพิ่ม Cloud Functions แยกจาก frontend พร้อมคำแนะนำการตั้งค่า Firestore, App Check และบริการส่งอีเมล

## สิทธิ์และการป้องกันการใช้งานผิดประเภท

- สมาชิกทั่วไปไม่สามารถอ่านรายการคำขอติดต่อได้ การล็อกอินอย่างเดียวไม่ให้สิทธิ์ทีม
- ตรวจ Firebase custom claim `admin: true` ทั้งที่หน้าเว็บและ Firestore rules
- ปิดการสร้าง/ลบคำขอจาก Firestore client; การสร้างผ่าน server เท่านั้น แอดมินแก้ได้เฉพาะ status, note และ updatedAt ที่ตรวจรูปแบบแล้ว
- ตั้งสิทธิ์แอดมินผ่าน script ฝั่งผู้ดูแลด้วย UID ที่ตรวจแล้ว ไม่เปิด endpoint ให้ผู้ใช้ยกระดับสิทธิ์เอง
- เปิด App Check สำหรับ public callable พร้อม rate limit ฝั่ง server และ honeypot ในฟอร์ม
- ข้อมูลลับของผู้ให้บริการอีเมลอยู่ใน server secrets ไม่อยู่ในตัวแปร `VITE_*` และไม่เขียนเนื้อหาฟอร์มลง log

## การแจ้งเตือนและความผิดพลาด

- เมื่อสร้างคำขอสำเร็จ ให้ client ทราบทันทีโดยไม่รออีเมล
- Firestore create trigger ส่งอีเมลผ่านผู้ให้บริการที่กำหนดและบันทึกสถานะการส่งในข้อมูลที่ client แก้ไม่ได้
- ออกแบบ worker รองรับ event ซ้ำ ใช้ idempotency ของผู้ให้บริการและบันทึกผลเพื่อจำกัดอีเมลซ้ำ พร้อม retry เมื่อเกิดข้อผิดพลาดชั่วคราว
- อีเมลมีข้อความแจ้งว่ามีคำขอใหม่และลิงก์หลังบ้าน ลดการคัดลอกข้อมูลส่วนตัวลงอีเมล
- หากขาดการตั้งค่า ให้แสดงข้อผิดพลาดตามจริง ห้ามแสดงว่าส่งสำเร็จหรือใช้ localStorage แทนฐานข้อมูล

## การทดสอบก่อนส่งมอบ

- ทดสอบ validation, submission ซ้ำ และผลลัพธ์เมื่อบันทึกล้มเหลว
- ทดสอบ rules ด้วย Firebase Emulator: guest และสมาชิกทั่วไปอ่านไม่ได้ แอดมินอ่านได้ แก้ข้อมูลได้เฉพาะช่องที่อนุญาต และยกระดับสิทธิ์ตัวเองไม่ได้
- ทดสอบ notification worker ด้วยผู้ให้บริการจำลอง: ส่งสำเร็จ, provider ล้มเหลว, retry และ event ซ้ำ
- ตรวจ frontend build และ lint รวมถึงฟอร์มบนจอเล็ก/ใหญ่ และรายการว่าง/โหลด/ผิดพลาด/ไม่มีสิทธิ์
- ก่อนยืนยันว่าใช้งานจริง ต้องทดสอบส่งฟอร์มบน deployment อ่านรายการด้วยบัญชีทีม และรับอีเมลจริงตามที่ผู้ใช้อนุญาต

## สิ่งที่ต้องตั้งค่าก่อนเปิดใช้งานจริง

- ผู้ใช้ระบุอีเมล `yada@myorder.ai` และ `sukanya@myorder.ai` สำหรับรับแจ้งเตือนและบัญชีทีมที่ต้องได้รับสิทธิ์ดูข้อมูล ต้องตรวจอีเมลที่ยืนยันแล้วและ UID ใน Firebase Authentication ก่อนกำหนด custom claim; การระบุอีเมลในเอกสารนี้ยังไม่ใช่การให้สิทธิ์จริง
- Firebase project และสิทธิ์ deploy พร้อมบริการ/แผนที่รองรับ Functions และ Firestore
- ผู้รับอีเมลแจ้งเตือนและ UID บัญชีทีมที่ยืนยันแล้ว
- ผู้ให้บริการอีเมล โดเมนผู้ส่งที่ยืนยันแล้ว และ secret ที่ตั้งค่าผ่านช่องทางปลอดภัย
- โดเมนหน้าเว็บสำหรับ App Check และลิงก์ไปหลังบ้าน

ข้อมูลเหล่านี้เป็น configuration สำหรับ deployment ไม่ควรฝังไว้ใน source code ส่วนการ deploy และการส่งอีเมลจริงจะรายงานผลแยกจากการเขียนและทดสอบโค้ด
